# Журнал настройки Kindle 4 (август 2026)

История отладки и решений: джейл, SSH, автозапуск, дизайн, живой конвейер, переезд на NAS, Wi-Fi.
Перенесено из личных заметок 2026-11-03. Runbook NAS — `dashboard/nas/README.md`, подсветка козырька — `backlight/README.md`.

## Архитектура

- **Софт:** jailbreak (пакетом с MobileRead) + USBNetwork (SSH) +
  **kindle-dash** — книга держит экран, кадры ей пушит NAS.
- **Рендер:** NAS (Synology) — Docker-контейнер `kindle-dash`: свой HTML-шаблон
  (не MagicMirror², от него отказались) + календарь по приватному iCal-URL
  Google + погода Open-Meteo → headless chromium → grayscale PNG 600×800 →
  ssh-пуш на книгу. Подробности — в разделе «переезд на NAS» ниже.
- **Корпус:** `~/dev/kindle-calendar/` — параметрический генератор Fusion 360
  (v0.2), печать PETG у друга на Bambu A1. Референс — «скульптура» с козырьком.
  5 деталей: фасад, задняя крышка (бобышки + M2.5), козырёк на штифтах,
  молочный диффузор, базовая плита с рельсами.
- **Подсветка козырька (v1):** Arduino Nano + энкодер + AO3401 + COB-нити —
  Nano только крутит яркость, без HomeKit (решение 2026-10-19). Схема —
  `backlight/README.md`.
- **Питание:** одно гнездо USB-C наружу (breakout с CC-резисторами 5.1k!),
  любая зарядка 5V/2A; внутри 5V-шина → Kindle (micro-USB хвост, D+/D−
  закорочены), ESP32, лента. LED к плате Kindle не подключать.
- **Battery eliminator — В ЭТОМ ПРОЕКТЕ НЕ ДЕЛАЕМ** (решение Димы 2026-08-27;
  батарея живая, 94%, книга на постоянном питании). Матчасть на будущее, если
  батарея умрёт: питать батарейную шину напрямую — DC-DC бак (MP1584/mini-360,
  ≥1 А, выставить **3.9 В** — ни в коем случае не 5 В!) с общей 5V-шины → на
  плату выпотрошенного родного пака (защита + NTC + разъём остаются, банка
  выкидывается). Если паять мимо платы пака — NTC эмулировать ~10 кОм на минус.

## Статус / ближайшие шаги

**Железо (2026-08-26):** прошивка **Kindle 4.1.0 (16153700055)**, серийник `B00E…`
= K4 NT silver (2011) → джейл поддерживается (диапазон 4.0.0–4.1.4).
Джейл — зеркало исходников NiLuJe **[KindleModding/K4-Jailbreak](https://github.com/KindleModding/K4-Jailbreak)**
(релиз v1.0.0, без логина на MobileRead), payload сверен по sha256 с исходниками.
**JAILBREAK ✅ прошёл 2026-08-26** — в `documents/` появился
`You are Jailbroken.txt`, установочные файлы система подчистила.
Uninstaller (`Update_jailbreak_1.8.N_uninstall.bin`) сохранён на маке.

**Канал root-доступа без MobileRead:** джейл выполняет `/mnt/us/runme.sh`
от root при каждом прогоне (повторять прогон безопасно) — это заменяет
USBNetwork-пакет, который лежит вложением за логином форума. Скрипт живёт
один прогон и умирает на перезагрузке, поэтому SSH ставим в два захода:
разведка → установка автостарта dropbear.
**Dropbear:** ARM-бинарь + rsync/sftp-server берём из зеркала
[azuwis/kindle-usbnetwork](https://github.com/azuwis/kindle-usbnetwork)
(старый, умеет только `ssh-rsa`/`ssh-dss` → для входа сгенерирован
**RSA**-ключ `~/.ssh/kindle-dash`, ed25519 не подойдёт).
**kindle-dash** ([pascalw](https://github.com/pascalw/kindle-dash)) — ровно
под K4 NT; ставится копированием в `/mnt/us/dashboard` (это и есть USB-раздел,
кладём с мака), шелл нужен только чтобы запустить `start.sh` и прописать
автостарт. **Релиз v1.0.0-beta.4 скачан и заточен под нас** (перекачать по тэгу):
`local/env.sh` → TZ `Europe/Kyiv`, `REFRESH_SCHEDULE="*/15 6-23 * * *"`,
`WIFI_TEST_IP=192.168.0.1`, батарея не мониторится; `local/fetch-dashboard.sh`
пока тянет пример-PNG (репойнт на NAS-рендер, когда поднимем MagicMirror²).
Бинари `next-wakeup` и `xh` в релизе — ARM, статик, заработают на K4.

### SSH-пакет: три захода (2026-08-26)

Ставится через **Update Your Kindle** пакетом OTA2, подписанным jailbreak-ключом
(KindleTool собран на маке, `-d kindle4`). Скрипт бежит root в основной системе.

- **v1** — механизм пакета рабочий (root, `mntroot rw/ro`, хуки ложатся), но
  dropbear не стартовал: `dropbearmulti` — multi-call бинарь, диспатчит по
  `argv[0]`, нужен под именем `dropbear`. Выяснилось: прошивка уже несёт
  `/etc/init.d/dropbear` + `/etc/dropbear` (свой RSA-ключ).
- **v2** — dropbear стартовал и слушал `0.0.0.0:22`, хуки (`rc5.d` + cron `*/5`)
  легли. НО: во время «Update Your Kindle» фреймворк опущен, **`wlan0` вообще не
  существует** (`ifconfig -a` = только `lo`) → достучаться некуда, а
  единственная строка лога лаунчера писалась на `/mnt/us`, который в этот момент
  отдан компу. После перезагрузки — порт 22 закрыт, ICMP молчит.
- **v3 (текущий, `Update_ssh_install_v3.bin`)** — чинит слепые зоны v2:
  1. журнал на `/var/local/sshd/boot.log` (переживает ребут, читается пока USB
     подключён; копия дублируется на `/mnt/us/kindle-boot.log`);
  2. **keepalive** — главный подозреваемый молчания: K4 гасит Wi-Fi в
     скринсейвере. Демон каждые 45 с давит скринсейвер (`preventScreenSaver 1`)
     и пингует шлюз, держа ассоциацию;
  3. **4 механизма автостарта** (rc2–5 + upstart-джоба + cron + врезка в родной
     `/etc/init.d/dropbear`) — v2 вслепую верил только в rc5.d;
  4. **запасной люк**: файл `USBNET` в корне раздела → лаунчер переключает
     кабель в ethernet-гаджет (`g_ether.ko`, `usb0 = 192.168.15.244`), SSH по
     проводу без Wi-Fi; само откатывается ребутом через 20 мин.
  Установочный лог v3 доложит, отрабатывал ли boot-хук вообще (mtime старого
  pidfile) и какой из механизмов реальный.

**Что доложил лог v3 (ответы на все вопросы):**

- ⚠️ **Дефолтный runlevel = 2** (`id:2:initdefault:` в `/etc/inittab`), а не 5.
  Поэтому одинокий хук v2 в `/etc/rc5.d/` не мог отработать **никогда**.
  v3 захукал rc2–rc5 → `rc2.d hooked`, и **cron подтверждён рабочим**
  (запись `trigger=cron`, `wlan0: <IP книги>`, порт 22 слушает).
- **upstart на этой прошивке нет** (`/etc/upstart` и `/etc/event.d` пусты) —
  только классический sysvinit.
- **`/usr/local/sbin/dropbear` отсутствует**, поэтому родной
  `/etc/init.d/dropbear` всегда выходит по `exit 1` — врезка в него мертва
  (безвредна). Свой бинарь в `/var/local/sshd/dropbear` обязателен.
- **`g_ether.ko` есть** (`/lib/modules/2.6.31-rt11-lab126/kernel/drivers/usb/
  gadget/`), плюс в прошивке живёт родной `/etc/init.d/usbnetd` → путь
  «SSH по кабелю» доступен.

### 🎯 Корень «книга пропадает из сети» — suspend-to-RAM (2026-08-26)

Не Wi-Fi, не автозапуск, не firewall. **Kindle засыпает в suspend-to-RAM**, и:

- Wi-Fi-чип продолжает **автономно отвечать на ARP** (offload), пока CPU спит →
  с мака это выглядит как «MAC в ARP есть, а ICMP и TCP мертвы». Именно эта
  картина сбивала с толку два захода подряд.
- **cron в suspend не тикает** — журнал лаунчера обрывается ровно на моменте
  засыпания (последняя запись 14:10, дальше тишина).
- `lipc-set-prop com.lab126.powerd preventScreenSaver 1` давит только
  скринсейвер и **от suspend не спасает** — keepalive из v3 оказался бесполезен.

⚠️ Мораль: SSH на стоковом K4 в принципе не бывает «всегда доступен» —
устройство спит по своей воле. Держать его бодрым может только тот, кто
остановит UI-фреймворк.

**v4 (`Update_ssh_dash_v4.bin`) — лечит причину, а не симптом:** запускает
**kindle-dash** хуком `rc2.d/S99zdash` (сортируется после `S99sshd`, чтобы SSH
поднялся первым). dash сам делает `/etc/init.d/framework stop` и забирает
управление сном → книга перестаёт засыпать самовольно.
Запуск с **`DEBUG=true`**: в `dash.sh` это подменяет `rtc_sleep` обычным
`sleep` вместо suspend → **книга не спит вообще, SSH стабилен** на время
настройки. Потом флаг снимается ради экономии (просыпание по RTC раз в 15 мин).
Также v4 делает `mount -o remount,exec /mnt/us` — vfat может быть noexec, что
убило бы ARM-бинари `xh` и `next-wakeup`.

🛟 **Предохранитель:** файл **`NODASH`** в корне USB-раздела → dash не стартует
на следующей загрузке, возвращается обычный UI. Mass storage при работающем
dash остаётся живым, так что люк достижим с мака.
⚠️ Имя флага на vfat регистронезависимо: файл `USBNET` конфликтует с папкой
`usbnet` — для аварийного ethernet-люка использовать другое имя.

## ✅ SSH + ДАШБОРД ЖИВЫ (2026-08-26)

`ssh -F ~/.ssh/kindle.conf kindle` → **root-шелл на книге**, dash крутится и
рисует картинку на e-ink. Обе версии-подозреваемые (suspend, firewall) оказались
**неверными** — ниже что было на самом деле.

### Что реально мешало (5 причин, все разные)

1. **Дефолтный runlevel = 2, а не 5** → одинокий хук в `/etc/rc5.d/` не мог
   отработать никогда. Лечится хуком в rc2–rc5.
2. **Зависший процесс dropbear с первой установки** (pid 10105, жил с 13:43):
   слушал `0.0.0.0:22`, но соединения не принимал. Помогла именно
   **перезагрузка** — сервер стартовал заново через хук при уже поднятой сети.
   ⚠️ `iptables` на прошивке **вообще нет** (`sh: iptables: not found`), так что
   firewall был ни при чём; cron всё это время тикал без пропусков
   (14:10/14:15/14:20/14:25) — suspend тоже ни при чём.
3. **Старые SSH-алгоритмы.** dropbear 0.53 (2011) предлагает только
   `diffie-hellman-group1-sha1,diffie-hellman-group14-sha1`, современный OpenSSH
   их отключил → `no matching key exchange method`. Лечится конфигом
   **`~/.ssh/kindle.conf`** (`KexAlgorithms +…`, `HostKeyAlgorithms +ssh-rsa`,
   `PubkeyAcceptedAlgorithms +ssh-rsa`, `Ciphers +…cbc`, `MACs +hmac-sha1`).
   ⚠️ `HostKeyAlgorithms +ssh-rsa,ssh-dss` → `Bad key types`; только `+ssh-rsa`.
4. ⚠️ **`Europe/Kyiv` — невалидная таймзона** для `next-wakeup`: встроенная база
   TZ знает Киев только как **`Europe/Kiev`**. Именно на этом падал dash.
5. **Нет корневых сертификатов**: `xh` → `Could not load PEM file
   "/etc/ssl/certs/ca-certificates.crt"`, причём **`--verify=no` не спасает** —
   CA-файл читается до запроса. Лечится бандлом с curl.se, положенным рядом
   (`/mnt/us/dashboard/ca-bundle.crt`) + `SSL_CERT_FILE` в `env.sh`.
   ⚠️ Имя `cacert.pem` ловит хук `block-secrets` (ложное срабатывание на `.pem`,
   файл публичный) — назвать `.crt`.

### Прочие грабли этой прошивки

- **`/mnt/us` — это `fuse.fsp`**, не vfat. `mount -o remount,exec` не проходит
  («mountpoint is not empty»), но **ARM-бинари оттуда выполняются нормально**
  (`xh 0.16.1`, `next-wakeup` работают). Переносить на `/var/local` не нужно.
- **`mntroot rw` молча не срабатывает в неинтерактивном SSH** → `ln` падает с
  Read-only. Использовать `mount -o remount,rw /` … `mount -o remount,ro /`.
- **busybox 1.7.2 беден**: нет `nohup`, `od`, `head -c`, `grep -E`; `ping -W`
  не поддерживается (печатает usage). Фоновый запуск — `( cmd >log 2>&1 </dev/null & )`.
- `dash.sh` **не подгружает `local/env.sh` сам** — это делает `start.sh`.
  Запуская dash напрямую, окружение подключать вручную, иначе
  «Missing required configuration. Timezone: (not set)».

### ⚠️ Автозапуск: rc-хуки МЕРТВЫ, всё живёт на cron (2026-08-26)

Проверка перезагрузкой вскрыла две неочевидные вещи — обе занесены сюда, чтобы
не наступить снова:

1. **`rc2.d/rc5.d/S99*` симлинки при загрузке НЕ выполняются.** Заголовки
   `boot.log` показывают: каждый пост-загрузочный старт — `trigger=cron`, ни
   одного `trigger=rc`. sshd поднимается только потому, что его каждые 5 мин
   дёргает cron (`*/5 * * * * /var/local/sshd/start-ssh.sh cron` в
   `/etc/crontab/root`). dash сперва имел лишь rc-хук → не стартовал никогда.
   **Вывод: единственный надёжный автозапуск на этой прошивке — cron.** dash
   теперь запускается тем же `start-ssh.sh` (он стал супервизором обоих),
   мёртвые `S99zdash` удалены. Задержка появления экрана после ребута — до 5 мин
   (worst case cron-интервал; типично ~1 мин).
2. **busybox `ps` показывает скрипты как `exe`** (без argv) → проверка живости
   через `grep dash.sh`/`grep sleep` не матчит НИКОГДА. Из-за этого супервизор
   плодил бы новый dash (и новый `framework stop`) каждые 5 мин. **Живость —
   только по PID-файлу** (`/var/local/sshd/dash.pid`): `( … exec sh dash.sh ) &`
   → `$!` = PID dash, дальше `kill -0`. Тот же приём у keepalive
   (`/tmp/sshd-keepalive.pid`).

### Текущая конфигурация

- **Автозапуск = cron `*/5`** через `start-ssh.sh` (супервизор): держит sshd
  (dropbear) + пробивает firewall + идемпотентно поднимает/перезапускает dash по
  PID-файлу. rc-симлинки не используются (S99sshd оставлен, но не работает;
  S99zdash удалён).
- dash запущен с **`DEBUG=true`**: `rtc_sleep` → обычный `sleep`, книга **не
  засыпает** и остаётся в SSH. Флаг зашит в супервизор `start-ssh.sh`; на
  постоянном питании его снимать НЕ надо (см. push-модель ниже).
- `framework stop` + `initctl stop webreader` отработали — родной UI отдал экран.
- **Сеть полностью открыта**: книга пингует мак, NAS и
  интернет. Изоляции IoT-сеть 2.4 ГГц **нет** → роутер править не нужно, мак на
  2.4 ГГц переводить не нужно.
- Батарея 94%, `gasgauge-info -c` работает.

### Решение: обновление ПО СОБЫТИЮ, а не по таймеру (2026-08-26)

Книга всегда на питании → расписание + suspend теряют смысл (они существуют
ровно ради батареи). Переворачиваем модель: **не книга опрашивает сервер, а NAS
будит экран, когда есть что показать**.

**Выбрано: push с NAS по SSH.** Механизм уже готов (рабочий ключ + `kindle.conf`).
NAS отрендерил PNG → залил на книгу → дёрнул `/usr/sbin/eips -g`. Задержка
1–2 с, в простое ноль трафика. Книга становится тупым сетевым e-ink дисплеем,
вся логика живёт на NAS, где её удобно править. Заливка уже проверена через
`ssh kindle 'cat > файл'` (scp/sftp-server на книге не установлен).

Отвергнутые альтернативы: **long-polling** (нужен эндпоинт, удерживающий
соединение — оправдан, только если NAS не сможет достучаться до книги сам);
**поллинг с ETag раз в 5–10 с** (просто, но задержка до 10 с и постоянное радио).

⚠️ **Ограничения e-ink, из-за которых «мгновенно» ≠ «непрерывно»:**
- частичное обновление ~0.5 с и копит ghosting; полное — чистит, но моргает
  всей панелью в чёрный. Отсюда `FULL_DISPLAY_REFRESH_RATE` (сейчас 4);
- ресурс панели конечен → минимальный интервал **не чаще 10–30 с** + дебаунс,
  чтобы серия быстрых событий схлопывалась в одну перерисовку.

**Плюс «пульс»:** раз в час полное обновление, даже если событий не было —
чистит ghosting и служит признаком жизни (застывшая вчерашняя дата = порвалась
цепочка).

**Порядок работ:** сначала рендер на NAS, потом переключение с таймера на push —
сейчас push слать неоткуда.

### 🚪 Как подключиться (шпаргалка для след. сессии)

```
ssh kindle          # ← алиас настроен в ~/.ssh/kindle.conf (legacy-алгоритмы)
```
Ключ `~/.ssh/kindle-dash` (RSA). Книга на `<IP книги>`, сеть IoT-сеть 2.4 ГГц.
Экран рисуется файлом `/mnt/us/dashboard/dash.png` (600×800). Перерисовать вручную:

Вернуть родной UI Kindle: положить файл `NODASH` в корень USB-раздела и ребут.

### ✅ ПЕРЕЕЗД НА NAS СОСТОЯЛСЯ (2026-08-27, день)

Мак больше не точка отказа. Конвейер живёт в Docker-контейнере
**`kindle-dash`** на Synology (`/volume1/docker/kindle-dash/`), мак остаётся
задокументированным резервом. PR: **[kindle-calendar#2](https://github.com/rudnik275/kindle-calendar/pull/2)**
(закрывает #1). Деплой/обновление — `dashboard/nas/install-nas.sh` с мака,
runbook — `dashboard/nas/README.md`.

**Живучесть при ребуте NAS — пять независимых слоёв:** `restart: always`
(проверено контрольным контейнером: падает сам → поднимается, RestartCount
растёт) + Container Manager стартует с DSM (`synopkg is_onoff` → on) +
весь стан на `/volume1` через бинд-маунт + всё зашито в образ (на старте не
нужны ни интернет, ни реестр — NAS грузится быстрее роутера) + watchdog в
`live-push.sh` (5 сбоев рендера или час без книги → `exit 1`, супервизор
поднимает с чистым Chrome). Плюс healthcheck по heartbeat в `docker ps`.
⚠️ Реальный ребут NAS НЕ делался (там Jellyfin, Plex, cloudflared, боты) —
это решение Димы; сами механизмы проверены по отдельности.

**Грабли, найденные при переезде:**

- ⚠️⚠️ **Бинарь dropbear из пакета kindle-usbnetwork собран с ЗАШИТЫМ путём
  `/mnt/us/usbnet/etc/authorized_keys` и `$HOME/.ssh/authorized_keys` не
  читает вообще.** Ключ, дописанный в `/var/local/sshd/authorized_keys`
  (откуда cron-супервизор копирует в `$HOME`), молча игнорируется: dropbear
  отвечает `0 fails`, ssh — `Permission denied`. Доказано прямо: с **пустым**
  `$HOME/.ssh/authorized_keys` старый ключ всё равно пускает. Это стоило
  самой долгой диагностики сессии — ложные версии (размер ключа, порядок
  строк, версия OpenSSH на клиенте) отпали одна за другой.
  **Новые ключи класть в `/mnt/us/usbnet/etc/authorized_keys`.**
- На книге есть **iptables** (`/usr/sbin/iptables`), и `start-ssh.sh` пробивает
  дырку только под порт 22 + ICMP. Отладочный dropbear на другом порту
  недостижим, пока дырку не пробьёшь вручную.
- `docker compose up --build` на DSM 7.3 **вешается намертво** (BuildKit не
  поднимается: ни промежуточных контейнеров, ни трафика, CPU ноль). Классический
  `DOCKER_BUILDKIT=0 docker build` работает — так и зашито в install-nas.sh.
  Первая сборка chromium на Celeron NAS — 15–25 мин.
- macOS от Sonoma подсовывает **openrsync** (protocol 29), который не
  договаривается с rsync 3.1.2 на DSM («unexpected end of file»). Деплой
  переведён на tar-over-ssh.
- Тональность: `sips -m "Generic Gray"` на маке и ImageMagick на Linux дают
  разную картинку. Свели эмпирически: `-grayscale Rec709Luma -gamma 0.83` →
  расхождение 1.75 уровня вместо 15. На 16-градационном e-ink это разница
  между сохранённой и съеденной фактурой пергамента.

**Два бага в собственном коде, вскрытых переездом:** (1) лок `live-push.sh`
лежал на постоянном диске, а в контейнере скрипт всегда PID 1 — лок, переживший
SIGKILL, с записью «pid 1» заставил бы следующий экземпляр увидеть «сам себя»
как чужого живого демона и выйти: вечный рестарт-цикл без единого кадра
(лок переехал на tmpfs); (2) первый кадр после старта писал копию в NAND книги
— в рестарт-цикле это выгрызало бы флеш (убрано, часовая копия осталась).

**События теперь автогенерятся:** `ical-sync.py` тянет приватные iCal-фиды
Google Calendar каждые 15 мин (RRULE разворачивается, таймзоны учтены, прошедшие
события отсеиваются, сбой сети оставляет прежние).

✅ **ПОДКЛЮЧЕНО 2026-08-27.** Приватный iCal-фид основного календаря лежит на
NAS в `/volume1/docker/kindle-dash/app/secret/ical-urls` (0600, root), на экране

URL = пароль на чтение календаря: в чат не вставлять, в репо не коммитить

### Диагноз Wi-Fi (2026-08-26) — железо ИСПРАВНО, сломан `wifid`

UI показывал `MAC: Unavailable` и «сетей 0» → выглядело как мёртвый радиомодуль.
Логи основной системы (`/var/local/log`, вытащены через diags) говорят обратное:

- `wpa_supplicant: Initializing interface 'wlan0'` + `Own MAC address:
  xx:xx:xx:xx:xx:xx` — интерфейс поднимается, драйвер `ar6003` работает.
- Прямой тест из diags: `SDIO: Enabled device mmc0:0001:1`, MAC прочитан из
  EEPROM, прошивка запрошена → **чип отвечает**.
- Единственная поломка: **`wifid`** (прослойка Amazon между UI и драйвером)
  падает `E main:exception:thread=main DEFAULT` сразу после старта и
  перезапускается по кругу — **6717 раз** в одном логе. UI берёт данные у неё,
  отсюда «Unavailable» и пустой список сетей.

**Для проекта это не блокер:** `wifid` обслуживает магазин/синхронизацию Amazon,
а дашборду нужен только поднятый `wlan0` — сеть можно держать напрямую
`wpa_supplicant` + `udhcpc`.

**✅ ВЫЛЕЧЕНО.** Виновник — `/var/local/system/wifid.conf`: зашифрованный профиль
сети прошлой владелицы от **июля 2013**, на разборе которого демон падал.
Файл (и заводской `hid.csv`, он был ни при чём — список хотспотов AT&T)
отложен в `.bak-preclaude`, бэкапы на USB-разделе в `wifid-backup/`.
После перезагрузки сети появились, **подключено к IoT-сеть 2.4 ГГц** (26.08).
Мораль на будущее: б/у Kindle с чужим Wi-Fi-профилем = крашлуп `wifid`,
лечится сносом `wifid.conf`, а не заменой железа.

**Карта разделов** (из diags): `mmcblk0p1` — основная система (358 МБ),
`p2` — диагностическая (64 МБ, откуда выполняется `runme.sh`),
`p3` — общий `/var/local` (32 МБ, виден из обеих), `p4` — USB-раздел (1.4 ГБ,
он же `/mnt/us`, смонтирован **noexec** → бинарники оттуда не запускаются,
класть в `/var/local`).

⚠️ **Сеть:** домашняя основная сеть — 5 ГГц, Kindle 4 её НЕ УВИДИТ (радио только
2.4 ГГц). Целевая сеть — **IoT-сеть 2.4 ГГц**. Пароль в переписку не передавать:
класть в файл на USB-разделе, скрипт заберёт и удалит.
